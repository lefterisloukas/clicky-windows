## In the case of slow TTS voice generation

Levers for Kokoro (local) TTS latency, if it ever feels slow again. Background: the current pipeline streams sentence-by-sentence — generation runs in a worker thread (`tts/kokoro-worker.ts`) and `TTSQueue` (`tts/queue.ts`) prefetches the next sentence while the current one plays, so inter-sentence gaps are ~0ms. See `docs/ADDITIONS.md` (2026-06-20, `fix/tts-playback-gap`) for the history. Grouped by which latency each attacks:

- **Do NOT "wait for the full reply, then generate it all at once".** Tempting, but it's a regression: it kills time-to-first-audio (you hear nothing until the LLM *and* TTS both finish — 5–10s of dead air on long replies) and Kokoro's ~510-token phoneme context means it still has to chunk internally anyway. Streaming + prefetch is strictly better for perceived latency.
- **Time-to-first-audio (the first sentence's unavoidable ~1s).** (a) *Short first chunk* — make the first chunk just the opening few words so audio starts almost instantly, then resume normal `MAX_CHARS` chunks (`tts/kokoro.ts`). (b) *Merge short adjacent sentences* up to the context limit to cut the number of generations.
- **Per-clip playback overhead (~100–300ms/sentence).** Today `playWav` writes a temp WAV and spawns a PowerShell `SoundPlayer` per clip. Replace with **gapless PCM streaming to the renderer's Web Audio API** over IPC — schedule buffers back-to-back, no process spawn, no temp files. This is the cleanest next win and removes the last residual per-sentence latency. (Same swap would also drop the `MediaPlayer`/`SoundPlayer` PowerShell paths in `tts/openai.ts` and `tts/elevenlabs.ts`.)
- **Raw generation speed.** *GPU execution provider* — onnxruntime supports DirectML on Windows; running Kokoro on the GPU can cut generation from ~1s to a few hundred ms (biggest single lever, but adds device detection + a dependency). Already on q4, the fastest CPU quant, so that lever is spent. The intra-op thread cap is at `cores/2` in `kokoro-worker.ts` — lowering it trades speed for system headroom, raising it does the reverse.
- **Deeper buffering (prefetch-N).** Generate several sentences ahead into an audio buffer instead of one. Only helps the edge case of a short sentence followed by a much longer one; otherwise playback (~3s) ≫ generation (~1s) so one-ahead already hides it. Probably not worth the added memory/complexity.
- **Different engine.** A frame-streaming TTS (emits audio *as* it generates, so even one long sentence starts immediately) — Kokoro-js doesn't do this; ElevenLabs' streaming/websocket API does, relevant only if going cloud.
